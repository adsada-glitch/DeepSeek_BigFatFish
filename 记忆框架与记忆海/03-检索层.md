# 03 · 检索层

记忆库到几百条以后，"把最重要的 80 条塞进提示词"就失效了——**最近几天的闲聊会把老底账挤出去**。

这一层解决"记得多了怎么挑"：每次唤醒按当前对话挑 6~10 条。

## 规则

```
库 ≤ 12 条   → 按权重全给（小库全量比检索准）
库 > 12 条   → 按当前对话检索
检索结果 < 3 条 → 回退按权重（避免这轮什么都没带）
```

第三条很重要：宁可带几条无关的，也不能让她"空着手"说话。

## 打分公式

```
score = 2.2 × 词汇重叠(IDF加权)
      + 1.2 × 主题命中
      + 1.0 × 新鲜度
      +     类型权重
```

| 分量 | 怎么算 |
| --- | --- |
| 词汇重叠 | 中文按字符 bigram 分词，重叠词按 IDF 加权（越常见的词越不值钱） |
| 主题命中 | 记忆的 `topic` 出现在当前对话里 |
| 新鲜度 | `exp(-距今天数 / 45)` |
| 类型权重 | 事实 0.3 / 约定 0.25 / 其它 0.15 |

IDF 的作用：`今天`、`什么` 这种词到处都是，不能靠它们匹配；`吉他`、`考试` 这种词稀有，命中了就应该高分。

## 停用词

中文分词后还要砍两类词：

- **单字虚词**：的、了、是、在、我、他、你、就、也、还……
- **双字虚词**：这个、那个、可以、不是、没有、这样、那样……

不砍的话，"我的""他的"会占满重叠分。

## 三个保底

光靠打分挑，日常碎话会全军覆没。所以有三道保底：

**1. 核心主题保底（最多 2 条）**

标了 `profile` / `owner-profile` 的记忆永远在场——"用户是谁"这种信息不该靠运气。

**2. 时段联想**

一句话没有查询词，但它其实是在问"这个点你在干嘛"：

| 命中 | 加分的主题 |
| --- | --- |
| 晚上好 / 晚安 / 睡了 / 困了 | 作息 |
| 早上好 / 起床 / 出门 | 作息、日程 |
| 考完 / 考试 / 分数 | 考试 |

命中后给对应主题 +0.9 分。

**3. 兜底补齐**

入选不足 4 条，或占用预算不到 40% 时，按"最近提过"补到 6 条（仍受字数预算限制）。

## 字数预算

不是按"条数"截断，是按**字数**：

```
预算 600 字（约 400 token）
装不下就整条跳过，继续试下一条更短的
```

为什么不截断：半句话的记忆比没有更糟——模型会顺着半句编。

## query 从哪来

从**桥接自己的最近消息快照**里取最近 6 条，拼成一段，最多 240 字。

关键：**不要用"模型会话的历史"当 query**。

对话会话会被重置、压缩、换新，而桥接的快照不受影响。用快照当 query，换会话之后检索照常工作；用会话历史，重置后前几轮等于没有 query。

## 和"按权重注入"的取舍

| | 按权重 | 按对话检索 |
| --- | --- | --- |
| 换会话后 | 稳 | 需要快照兜底 |
| 聊到第十轮 | 可能塞了一堆无关的 | 准 |
| 提示词成本 | 80 条 ≈ 2.4k token | 6~10 条 ≈ 0.4k token |
| 库容量 | 120~200 | 500~2000 |

两者不是替代关系，是**阶段关系**：库小的时候权重更稳，库大了检索才划算。

所以切换阈值写死在代码里（12 条），也可以一键退回：

```json
{ "memory": { "retrieval": "weight" } }
```

## 效果

同一批记忆，两种注入方式的对比（示例）：

| 场景 | 按权重注入 | 按对话检索 |
| --- | --- | --- |
| 用户问"上次那家店叫啥" | 前 80 条里不一定有 | 命中"店名"那条 |
| 用户说"晚上好" | 前 80 条按权重铺开 | 保底带作息 + 最近的事 |
| 每轮成本 | 2.4k token | 0.4k token |

## 已知不足

- **同义词不认**："馆子"和"餐厅"是两回事，因为没有向量
- **跨语言不行**：中英混写会漏
- **长记忆会被稀释**：一条 120 字的记忆，重叠分会被平均掉

到几千条、或者需要语义匹配时，再加嵌入模型。在那之前，这层的性价比最高。
