# 01 · 整体架构

## 五个部分

| 部分 | 职责 | 是否必需 |
| --- | --- | --- |
| **OneBot 网关** | QQ ↔ 程序，把消息变成 JSON | 必需 |
| **桥接程序** | 攒消息、拼提示词、管记忆、发回复 | 必需 |
| **模型** | 生成回复、决定调哪个工具 | 必需 |
| **记忆内核 + 日记** | 长期记忆与流水 | 可选，但这是"她记得"的来源 |
| **记忆海** | 把记忆画出来给人看 | 可选，纯观赏 |

拆开的原因是：**只有桥接是"单写者"**。记忆、日记、快照都只由它写，其他进程只读。这样不会出现两个进程同时改一个 JSON 的经典事故。

## 数据流

```
用户消息
   │
   ▼
[网关] ──▶ [桥接：合批 6 秒] ──▶ [拼提示词] ──▶ [模型]
                                      ▲              │
                                      │              ▼
                              [记忆 + 情绪]      [工具调用]
                                      ▲              │
                                      └──── [写记忆] ◀┘
                                                     │
                                                     ▼
                                              [发回 QQ]
```

## 桥接每轮做的六件事

1. **合批**：窗口内到达的消息合成一次唤醒（默认 6 秒）
2. **取状态**：未读数、最近消息、上次发言时间
3. **取记忆**：小库全量、大库按当前话题检索（见 03）
4. **拼提示词**：角色、状态、记忆、情绪、节奏规则，顺序固定
5. **交付模型**：模型可能多步调用工具
6. **发送**：分条、控制间隔、写回快照

## 提示词的固定顺序

顺序本身就是优先级。排在前面的更"硬"：

```
角色 → 身份 → 令牌 → 初始设定 → 反AI味 → 积极性
→ 表情策略 → 回复节奏 → 此刻状态 → 唤醒原因
→ 记忆 → 记忆纪律 → 参与度 → 沉睡前规则 → 时间感
```

两个经验：

- **"该记什么"必须每轮都在眼前**。只写在角色卡里等于没写——实测 24 小时 60 次工具调用、0 次写记忆，就是因为这条只在她主动查角色卡时才看得到。
- **时间感放最后**：紧挨着唤醒原因和行动指令，位置最显眼。

## 记忆的三种"寿命"

| 类型 | 存哪 | 寿命 | 谁写 |
| --- | --- | --- | --- |
| 事实/约定/偏好 | `memory-state.json` | 权重决定，通常几周到几个月 | 模型调工具 |
| 情绪 | 同上 | 3 天 | 桥接自动 |
| 日记 | `diary/YYYY-MM-DD.md` | 400 天 | 定时脚本 |
| 最近消息 | `social-v2.json` | 每会话 100 条 | 桥接自动 |

## 一个反直觉的设计

**日记不调模型**。

一开始想让模型每天写一篇"今天发生了什么"，后来砍了：一是贵，二是模型会编。现在的做法是脚本按模板抽关键词和流水，稳、免费、可回看。

模型要"回忆"时，让它自己用关键词去搜日记，而不是提前嚼一遍。

## 为什么不把所有记忆塞进向量库

成本对比（单会话、每天 20 条、跑一年）：

| 方案 | 每轮开销 | 维护成本 | 远处的记忆 |
| --- | --- | --- | --- |
| 全塞向量库 | 每次检索 + 大段上下文 | 要嵌入模型、要建索引 | 好 |
| **关键词 + 权重 + 检索** | 固定 6~10 条 ≈ 400 token | 零依赖 | 够用 |
| 不记忆 | 0 | 0 | 没有 |

结论：**在单会话、千条以内，关键词检索的性价比远高于向量**。到几千条再考虑加嵌入。
